# Hush MVP – Decisions

Outcome of the design grilling session (2026-10-22). Refines [project-brief.md](project-brief.md); where they differ, this document wins.

## Platform & stack
- **Windows only** for the MVP. Keep code free of platform-specific shortcuts so macOS/Linux can follow.
- Tauri 2 + **Svelte 5** + TypeScript + Vite, CodeMirror 6, **npm**.
- rusqlite with **`bundled-sqlcipher-vendored-openssl`** (OpenSSL libcrypto compiled from source and statically linked; needs Strawberry Perl at build time). SQLCipher needs a crypto provider; vendoring avoids system OpenSSL on Windows.
- Bundle identifier `com.redheadit.hush`. No licence file for now.

## Vaults & security
- Multiple vaults (one SQLCipher file each, extension `.hush`). Unlock screen offers "Open existing…" / "Create new…" and remembers recent vault **paths** in an app config file — paths only, never content or key material.
- SQLCipher default KDF (PBKDF2). Passphrase/key never written to disk. **No recovery**: the create screen states this plainly.
- Change passphrase via `PRAGMA rekey`.
- **Multiple instances** (2026-10-24): several Hush processes may run at once, each on a **different** vault (no single-instance plugin; each process has its own connection, key and auto-lock timer). The same vault is never open in two processes: opening takes an exclusive OS lock on `<vault>.hush-lock` next to the vault (not on the vault file itself, which on Windows would block SQLite), before the key is derived. A second open fails with "already open in another Hush window". The lock is released on lock, close and crash. The shared app config is re-read on every use and updated under an OS lock (`config.json.lock`), so concurrent recent-vault writes are not lost.
- Auto-lock after N minutes idle (default 10, 1–1440, stored inside the vault) and on demand (Lock button, Ctrl+L). Enforced by a backend timer; the frontend only reports activity. Idle time uses both the monotonic and wall clock so a machine waking from sleep locks immediately. OS sleep / screen-lock hooks deferred to v2.
- On lock: close the connection, zeroize the key in Rust, wipe frontend state.
- Preview: Markdown rendered with raw HTML **disabled**, output sanitised with DOMPurify. Strict CSP blocking all remote loads (images, scripts, fonts). External links open in the system browser, on click only.
- ~~Delete is a hard delete with confirmation.~~ Replaced by a **trash** (2026-10-24, see Notes). `PRAGMA secure_delete=ON` stays for every real delete. Trade-off accepted: deleted text stays in the (encrypted) vault file until purged, so anyone who later gets the passphrase can read notes deleted within the retention window; that person can already read every live note, and the trash protects against accidental permanent loss.
- No export in the MVP.
- No note content in logs; devtools disabled in release builds.

## Notes
- Identity: **`(folder, title)` is unique**, not the title alone. `folder` is the full path (e.g. `archive/2019/march`), indexed.
- Title is a separate field (from the filename on import). Renaming happens in the title field.
- Autosave 500 ms after typing stops; no save button.
- **Multi-select** (2026-10-24): in both the Tree and Recent views, Ctrl/Cmd+click toggles a note, Shift+click selects a range of visible notes, Ctrl/Cmd+A selects every visible note, Escape clears; a plain click opens the note. Only notes can be selected, never folders. An action bar offers Move to… and Delete. Bulk move is one transaction with one link-preserving pass, all or nothing on any `(folder, title)` clash. Bulk delete moves to the trash, also all or nothing.
- **Bulk metadata edit** (2026-10-24): the multi-select action bar's Edit… adds or removes a tag, or sets the topic, author or rating, on every selected note. Each edit rewrites the note's frontmatter and re-derives it like a save, in one all-or-nothing transaction; notes it wouldn't change are left alone, changed ones get `updated_at` bumped. Remove tag only edits frontmatter, never inline `#tags`, and reports the notes that still have the tag inline. A singular `tag:` key is folded into `tags`. Notes whose frontmatter can't be read are skipped and reported rather than rewritten.
- **Trash** (2026-10-24): Delete moves a note to the trash, with no confirmation since it can be undone. Trashed notes are hidden everywhere: note list, folder tree, search, filters, facets, link resolution, backlinks and outgoing links (links to them show as unresolved). They keep their row but lose their tag, attribute and link rows, which are derived again on restore.
  - *Delete forever* on a note skips the trash (with confirmation). The Trash view lists trashed notes with their original folder and deletion date: Restore, Delete forever, Empty trash (both with confirmation, real deletes).
  - Restore goes back to the original folder; if `(folder, title)` is taken by then, the note becomes `Title (restored)` (then `(restored 2)`, …). It runs the same link-preserving rewrite as create.
  - Auto-purge on unlock: trashed notes older than N days are deleted for good. Default 30, 0 = never, stored in vault `settings` (`trash_days`) and editable in Settings.
  - **Folder delete** (2026-10-25, #54): right-click (or Shift+F10 / the menu key / Delete) on a folder row → *Move folder to trash* moves the folder with every live note in it and below it to the trash as **one entry**. It always asks, with counts from the backend (`folder_contents`: *Move “Projects” and everything in it to the trash? 1,234 notes in 56 subfolders.*), even when "Confirm before deleting" is off, because one click can trash a large part of the vault. A folder that exists only in the tree (no notes) is removed without asking. The tree forgets the folder's expanded/loaded state, the "New note in" folder falls back to the parent, and an open note inside is closed.
  - Groups are stored in `trash_folders(deleted_at PRIMARY KEY, folder)` (migration 10, additive). A group's notes are the notes with that `deleted_at`: every trash operation takes its own `deleted_at` (now, or one past the latest in use), so the key alone finds them, through the `notes_deleted` index. Notes already in the trash stay separate entries. Restore brings the whole group back in one transaction, with one link-preserving pass over all its titles and the "(restored)" rule per clashing note; Delete forever and auto-purge (same `deleted_at`) remove it as a whole. A group whose notes are all gone some other way is dropped.
  - Set-based: one `UPDATE notes` and one `DELETE … WHERE note_id IN (SELECT id FROM notes WHERE deleted_at = ?)` per derived table. The folder match is one range on the `folder` index (`folder >= f AND folder < f||'0' AND (folder = f OR folder > f||'/')`); `move_folder` uses the same match now instead of a `substr` scan. Vectors are deleted on trash as for single notes, so a restored folder is re-embedded by the background job: at the measured 13 notes/s that is about 2 h for 100k notes. **Measured** (release build, 4-core Xeon 2.8 GHz Linux container, 100k notes in 400 subfolders plus 10k others): count 43 ms, trash 1.1 s, first trash page 24 ms, restore 3.2 s.
  - The Trash view is paged (200 entries, "Show more"): `trash_entries` returns folder groups and loose notes, newest first; the footer count is `trash_count`.
- Editor: split view (source | preview) with a preview-only toggle. Live preview deferred to v2.
- **Frontmatter in the body is the single source of truth.** Author, topic, tags and attributes are derived from it on every save. The metadata panel edits the frontmatter.
- Tags = inline `#tags` ∪ frontmatter `tags`.
- **Tag rules** (2026-11-04, #122): imported vaults were full of tags nobody made (`#a` from anchor links, `#fff` and `#1e1e1e` from CSS, `#include` from indented C, `#1` from `tags: [1, 2]`). One function, `markdown::is_tag`, decides for inline tags, frontmatter tags, import rules (`tags_of`) and tags typed in the metadata panel or Settings: a tag needs **at least two characters and a letter** (`\p{L}`), and isn't an ordinal (`1st`, `22nd`) or a **hex colour with a digit** (`1e1e1e`, `a0a0a0`, `f00`). All-letter hex words (`cafe`, `bad`, `fff` in prose) stay tags; `#2024-review`, `#3d`, `#v2` stay too. Inline, `markdown::parse` also skips markdown link targets (`](#…)`), bare URLs, HTML tags with their attributes and `<style>` blocks, indented code blocks (four spaces or a tab after a blank line; indented list items and lines inside a list or a paragraph aren't code), and a hex colour followed by `;` or `}` (`color: #fff;`). Frontmatter values that aren't tags stay in the frontmatter (`Parsed::frontmatter_tags` keeps them), so editing the tag list never drops text the user wrote. Bump `markdown::TAG_RULES_VERSION` whenever these rules change.
- **Re-deriving tags once per rules version** (#122): no schema migration. On unlock a background pass (`retag`, Activity panel row *Tag rules*) compares the vault setting `tag_rules_version` with `TAG_RULES_VERSION`; when they differ it re-derives every live note's tags, 500 notes per vault access in note-id order with a 5 ms pause between pages, through `with_vault_quiet` (never counts as activity), holding off while an import runs and stopping on lock. Progress is kept in the setting `tag_rules_progress` (`version:note id`), so a pass cut off by a lock goes on where it was. Bodies are only read: a note's `note_tags` rows are rewritten only when its tags differ, and `updated_at`, the embedding queue and the full-text index are untouched. At the end it deletes `tags` rows no note has and the classifier heads (`tag_heads`) of those tags, then writes the setting. Descriptions and feedback are the user's own and stay (a described junk tag stays listed by its description). Cost: one body read and parse per live note, once. Measured (release, 4-core container, `tests/scale.rs` `retag_benchmark`, 100,000 generated notes of ~300 words): **2.9 s** for all 201 pages, median page **14 ms**, longest **51 ms** (the longest the vault is held), the job with its pauses **3.9 s**; at 1M that is about 30–40 s in the background, once.
- **Tags are case-sensitive** (2026-10-24): `jr`, `Jr` and `jR` are different tags, everywhere (dedup, filters, nested-tag matching). Lists sort ignoring case. Folders, titles, author, topic and attributes stay case-insensitive. Import rule maps prefer an exact-case entry and fall back to ignoring case.
- Author: free text, defaults to a vault-level "default author" setting.
- **Rating** (2026-10-25, #56): frontmatter `rating`, a whole number 1–5 (`rating: 4`; `"4"` is accepted too); no key = unrated. Derived into `notes.rating` (`CHECK 1–5`, partial index `WHERE rating IS NOT NULL`, migration 11) like author and topic, so "4 stars or more" is a range. Any other value (`4.5`, `five`, `0`, `9`, a list) is not lost: it stays a generic attribute, the note counts as unrated, and the details panel shows it under Attributes. The migration moves a note's single valid `rating` attribute into the column and leaves the rest. Details panel: a row of 5 stars (a `radiogroup`; arrows, 1–5, Home/End set it, 0/Delete/Backspace clear; hover previews; clicking the current star or the × clears). Bulk *Set rating* (`MetadataEdit::SetRating`, `null` clears; setting or clearing also replaces an invalid value). Filters: Rating Any / ★ 1+ … ★ 4+ / ★ 5 (`min_rating`, `rating >= ?`, unrated never matches). Without search text that filter reads the rated notes through `INDEXED BY notes_rating` and sorts them by updated: left alone, SQLite walks `notes_updated` and checks every note, which reads the whole vault when few notes are rated. Rated notes show `★4` in the tree and the note list. Sorting by rating is not offered (no sort control exists yet).
- **Read status** (2026-11-04, #124): unread / partly read / read, set by hand (details panel, bulk *Set read status*); opening a note doesn't change it. Stored in `notes.read_status` (0/1/2, `NOT NULL DEFAULT 0`, `CHECK 0–2`, migration 12), not in frontmatter: it is about the reader, not the note, so marking doesn't rewrite the body, bump `updated_at`, re-index or re-embed (the embedding triggers watch title, body and deleted_at only). Cost: an export/re-import loses it. Existing and imported notes are unread. Filters: Read status Any / Unread / Partly read / Read / Not finished (unread + partly read). Without text, Partly read and Read read the partial index `notes_read (read_status, updated_at) WHERE read_status > 0` in order (`INDEXED BY`, unless the rating filter has its own); Unread and Not finished walk `notes_updated` like no filter, which fills a page at once while most notes are unread. The tree and note list show `◐` (partly read) and `✓` (read); unread has no marker.
- Topic: free field, defaults on import to the top-level folder relative to the import source (not the target folder); rules can override.
- Folders exist implicitly through their notes. Move a note by editing its folder; empty folders can be created from the tree (they are not stored, so one without notes disappears on lock).
- New notes are titled "Untitled", "Untitled 2", … in the selected folder, with the default author in their frontmatter. Shortcuts: Ctrl+N new note, Ctrl+K search, Ctrl+L lock, Ctrl+F find in note, Ctrl+H find and replace (Cmd+Alt+F on a Mac). Folder rename deferred to v2.

## Links
- Stored as `links(from_note_id, target_text)` and resolved at query time.
- Obsidian-style resolution: `[[Title]]` if the title is unique, otherwise the shortest unique path `[[archive/2019/Title]]`.
- `[[Title|alias]]` fully supported. `[[Title#Heading]]` links to the note (no heading jump yet). No embeds.
- Ambiguous link: warning style, click opens a picker. Unresolved link: distinct style, click creates the note.
- A note whose folder *equals* the link path wins outright (so `[[T]]` → root `T`, `[[a/T]]` → `a/T` over `x/a/T`); otherwise every folder *ending in* the path matches.
- Rename, move **and create** preserve meaning: any link that resolved uniquely before the change but not after is rewritten to the shortest unique link of its original target (keeping `#heading` and `|alias`), in the same transaction. Bulk import skips this and reports ambiguities instead.
- **Backlinks and outgoing-links panels** (2026-10-26, #79): two collapsible sections in the details panel, under Details and above Related. *Backlinks* lists each linking note (title, folder) with the line around its first link to the open note, trimmed to 160 characters around the link (`…` where cut), computed from the linking note's body when the panel loads; a link that also matches other notes is marked "ambiguous link". *Outgoing links* lists each distinct target as written, with the note it resolves to, or "ambiguous: N notes" / "unresolved" in muted italics; a click follows it like a click in the preview. Commands: `backlinks`, `outgoing_links`, `resolve_link` (target plus the summaries of the notes it resolves to), `create_linked_note`. Both panels and Related reload when another note opens, after the open note is saved, and after a bulk move, folder move, metadata edit, tag accept or trash from the sidebar (the operations that can rewrite or remove links while the note view is shown; import, trash restore and settings are separate views, and the panel reloads when the note view comes back). The collapsed state of Backlinks, Outgoing links and Related is one vault setting, `details_collapsed` (comma-separated section names); Related was not remembered before.
- **Clickable wikilinks** (#79): the preview renders `[[target#heading|alias]]` as a link (markdown-it inline rule, same reading as `markdown::parse`: not in code, not `![[embeds]]`, `[[#heading]]` stays text) showing the alias or the target text. A click resolves the target then: unique opens the note; ambiguous opens a menu at the click listing the candidates by `folder/title`; unresolved opens a menu offering *Create "target"*, which creates the note in the link's folder (`path/Title`) with the default author and opens it. The preview does not style ambiguous or unresolved links differently: that would mean resolving every link on each render (each keystroke); the Outgoing links panel shows their state instead.

## Data model
- `notes` (id, folder, title, body, author, topic, rating, read_status, created_at, updated_at, deleted_at), `(folder, title)` unique among live notes (partial index `WHERE deleted_at IS NULL`); `deleted_at` set = in the trash
- `tags` (id, name), `note_tags` (note_id, tag_id)
- `note_attributes` (note_id, key, value), indexed on `(key, value)`
- `links` (from_note_id, target_text)
- `notes_fts` (FTS5 over title and body)
- `settings` (key, value) — auto-lock minutes, default author, trash retention days, …
- `import_rules` (see Import)
- `note_embeddings` (note_id, model, content_hash, vector), primary key `(note_id, model)` (see AI classification)
- `tag_descriptions` (tag, description, vector, model) and `tag_feedback` (note_id, tag, accepted, created_at), primary key `(note_id, tag)` (see AI classification, Tag suggestions)
- `tag_heads` (tag, model, weights, bias, n_pos, n_neg, precision, recall, trained_at, inputs) (see AI classification, Tag classifiers)
- `trash_folders` (deleted_at, folder): folders deleted as a whole; the group is the notes with that `deleted_at` (see Notes, Trash)
- `embedding_dirty` (note_id, version): notes whose vector may be out of date, and `embedding_gone` (note_id): notes deleted for good since the job last looked; both filled by triggers (see AI classification, Background job)
- WAL mode. Indexes on folder, topic, author, updated_at, created_at, note_tags.

## Search
- FTS5, bm25 ranking, highlighted snippets, search as you type (~150 ms debounce).
- **At 1M notes** (2026-10-25, #51; before: `t` 18–20 s, `the` 8–12 s per keystroke):
  - **Prefix index** `prefix='2 3'` on `notes_fts` (migration 9 drops and refills the index from `notes` in batches of 2,000, reporting progress to the unlock screen after the first second; derived data, so no note content is at risk). A 2- or 3-letter prefix reads one list instead of merging every word that starts with it. The refill took ~11.5 min at 1M notes on the 4-core Linux container (measured with FTS5 `rebuild`) and grows the vault by about a third of the old index's size.
  - **One letter is a whole word**, not a prefix: `t` matched nearly every note. Prefixes start at two characters.
  - **Bounded ranking:** a query first counts its matches up to `RANK_LIMIT` (10,000), from the full-text index alone (the trash filter is answered from the trashed ids, not by joining every match to `notes`). Up to 10,000 matches are ranked by bm25 as before; above that the list shows the **newest matches** (highest note id) with "Many matches, newest first. Type more to sort by relevance." The issue's default was bm25 within the first 50,000 matches, but bm25 reads each query word's whole list to weigh it, so for a common word ranking costs ~150–250 ms whatever the cap; newest-first reads only the page shown.
  - **Snippets and summaries only for the page shown** (200 notes), not for every match.
  - **A newer search cancels an older one**: the session interrupts the older search's running statement (`sqlite3_interrupt`; only ever while a search, never a save or a job, is running on the connection) and the older search also stops between steps; it returns `cancelled`, which the frontend drops. A search still waiting for the vault when a newer one starts doesn't run.
  - With metadata filters the matches are still joined to `notes` (filters on tags, folders, dates and attributes at 1M notes are not covered here).
  - **Measured** with the scale benchmark at 1M notes on the 4-core Linux container (median of 5; before → after): `t` 18.7 s → 0.1 ms (no note has the word *t*; it no longer matches every word starting with t), `th` 9.1 s → 26 ms, `the` 8.0 s → 24 ms, two words (`but monmoldaind`) 284 → 256 ms. The two-word case misses the 150 ms goal: one of its words is in nearly every note, and bm25 reads that word's whole list to weigh it.
- **Phrases** (2026-11-04, #116): words in double quotes must appear together, in that order (`"9 years"`); an unclosed quote runs to the end, and its last word is a prefix while typing (`"9 yea` finds "9 years"), a closed quote is finished. Several words without quotes still find every note with all of them, but when the results are ranked (up to `RANK_LIMIT` matches) notes with the words as a phrase come first, then bm25. Above `RANK_LIMIT` the list stays newest first and the phrase isn't read. Snippets of phrase matches highlight the phrase as one span. **Cost** at 1M notes (`phrase_order_at_1m_notes`, release, 4-core Linux container, 9,091 matches, median of 5): `9 years` 565 ms against 580 ms for the same query without the phrase order (no difference; the time is the prefix `years*`), `9 years ` (finished) 89 against 81 ms; `many years` (100,000 matches, newest first) unchanged.
- Filters: tags (multi-select, AND), topic, author, folder, date range (created/updated toggle), attribute key = value.

## Import
- Source: a folder of notes (an Obsidian vault, or the archive: Markdown, text, HTML, RTF, Word, PDF, …). Real data is mostly an online archive with partial, malformed HTML. Real files are not available on the dev machine: develop against a **dummy fixture vault** (~20 files) that mimics them.
- Background task with progress and cancel; tens of thousands of files expected; transactions in batches of 500. Note list is virtualised.
- Dry-run preview (before/after samples, per-file warnings) before anything is written; the Import button is only enabled after a full preview of the same folder. Source folder never modified. Raw text is not kept.
- **Best effort: every readable file is imported**, judged by extension and content (2026-10-24):
  - Markdown and plain text (including unknown extensions, and files without one, that turn out to be text) are cleaned as below.
  - `.html`/`.htm` documents are converted whole; `.rtf` goes through a built-in converter (text, paragraphs, special characters, Unicode). A file with the wrong extension is recognised by its content (`{\rtf`, `<!DOCTYPE html`).
  - Data and code (`.csv`, `.json`, `.xml`, `.log`, `.ini`, scripts, …) are kept verbatim in a fenced code block, since joining "wrapped" lines would corrupt them.
  - Encodings: UTF-8, UTF-16 with a byte order mark (Notepad "Unicode"), otherwise Windows-1252 (a superset of Latin-1), with a warning. Line endings become `\n`.
  - Binary files (known extensions, file signatures, NUL bytes) are not imported yet and are counted per format in the report; **Word, PDF and other formats come later**. Text files over 10 MB are skipped and listed. `<page>_files` folders saved next to a web page are counted as page assets, not imported.
- **Target folder** (2026-10-24): after picking a source folder, an editable target folder is pre-filled with the source folder's name (`D:\Archive\OldVault` → `OldVault`); clearing it imports into the vault root. Note folder = target + the path relative to the source, normalised. If the target already holds notes the UI warns that the import merges into it, and the dry run shows how many notes would be skipped because their `(folder, title)` exists, plus every final folder path. Changing the source or the target requires a new full preview before Import is enabled.
- Hidden files and folders (`.obsidian`, `.trash`) are skipped. Folder = target folder + path relative to the source; title = file name (characters titles can't hold are replaced, with a warning). Files with the same name in one folder (`letter.rtf`, `letter.txt`) are kept apart: later ones get their extension added (`letter (txt)`). A note whose `(folder, title)` already exists in the vault is skipped, so re-importing a folder adds only what is new.
- **HTML cleanup per block**: split on blank lines; only blocks containing tags go through a tolerant HTML5 parser (`html5ever` via `htmd`); unclosed tags are closed at block end; unconvertible markup is dropped and reported. Blocks with block-level tags are converted whole; blocks with inline markup only keep their line structure (paragraphs via a line-break placeholder, lists line by line), so Markdown lists, `[[links]]` and `#tags` mixed with HTML survive. Code blocks are never touched.
- **Unwrap hard wraps** inside paragraphs; leave headings, list items, quotes, code blocks, tables and blank-line breaks alone; never join a line ending in two spaces (or `\`). A line is only joined to one of at least 50 characters, so short lines written on purpose (greetings, poems) stay as they are.
- **Label/attribute rules** (user-configurable, stored inside the vault, run at import only):
  - `source`: filename | frontmatter | first N lines | body
  - `pattern`: Rust `regex` (linear time; no lookarounds/backreferences)
  - `target`: tag | author | author_email | topic | created_at | attribute:<key>
  - `map`: optional value mapping (e.g. `jr → Journal`, `dr → Dream`)
  - `strip`: remove matched text from the body
  - `strip`: on the file-name source it removes the match from the title instead.
  - Single-valued targets take the first match of the first matching rule; tags and attributes collect every match.
  - Test button previews matches against a pasted sample. Frontmatter is read natively, so the defaults are the archive's mail-style headers (`From:` → author and `author_email`, `Date:` → created, `Subject:` → `subject` attribute, all stripped) and one label rule (`jr`/`dr` in the file name → `journal`/`dream` tags, stripped from the title).
  - Rule results are written into the note's frontmatter, as is the default topic when there is none: the top-level folder relative to the import source, ignoring the target prefix. Files directly in the source root get no default topic.
- `created_at` precedence: rule match → frontmatter `created`/`date` → date in filename → file mtime. `updated_at` = file mtime.
- Import report lists warnings and ambiguous links.

## AI classification
**Embeddings** (2026-10-24): every note gets a vector computed inside the Hush process by a local model and stored in the vault. It is the base for related notes, tag suggestions and tag discovery. No note content leaves the machine or the process; English only.
- **Model:** `BAAI/bge-small-en-v1.5` (MIT; 384 dimensions, 512-token context), the int8-quantized ONNX export from `Xenova/bge-small-en-v1.5` (`onnx/model_quantized.onnx`, 34 MB), run with ONNX Runtime through the `ort` crate and tokenized with `tokenizers`. Model ID `bge-small-en-v1.5-q8`.
- **Bundled, not downloaded at runtime.** `npm run fetch-model` (run before `tauri dev`/`tauri build`) fetches the ONNX file and `tokenizer.json` into `src-tauri/models/` (gitignored) and checks them against the SHA-256s pinned in `models/manifest.json`; a test keeps the manifest equal to the model descriptor. They ship as Tauri resources with the model licence. On load Hush reads each file into memory, checks its SHA-256 and loads the checked bytes, so a mismatch (or a missing file) stops indexing and nothing else changes; Settings → Model and the footer say which file and which features are off (see Model section).
- **Network rule** (changed 2026-10-26, #83; was "Hush itself never goes online"): Hush goes online only when the user clicks *Download* for an optional model in Settings → Model, and only to the URLs pinned in that model's descriptor. `ureq` is the one HTTP client (`cargo tree -e normal` shows no other: no `reqwest`, `hf-hub` or `hyper`), and only `embed::download` uses it; see Optional models. ONNX Runtime itself is downloaded at build time by `ort` (`download-binaries`, linked statically on Windows); its telemetry is turned off.
- Inference uses at most half the CPU cores (ONNX Runtime intra-op threads), so the UI stays responsive. Settings → Indexing → **Use all cores while indexing** (#49) uses every core instead; it is a choice for the machine, kept in the app config (`index_all_cores`), not in a vault, and applies from the job's next pass (the model is reloaded with the new thread count).
- **Ready for other models:** everything model-specific is in one `ModelDescriptor` (`src-tauri/src/embed/mod.rs`): ID, file names, URLs and SHA-256s, vector dimensions, max tokens per chunk, token pooling (CLS for bge), chunk pooling, text prefix, default suggestion threshold. No other code assumes a vector length or chunk size; a vector's length comes from its BLOB.
  - The active model is the vault setting `embedding_model` (default the bge ID). `embedding_model_ready` names the model whose vectors are complete; everything that reads vectors uses it, so after a switch the old vectors keep serving until the new model covers every note. The job then sets `embedding_model_ready` to the new model and deletes the other model's rows.
- **What is embedded:** title + body **without frontmatter** (it holds the tags, which would leak the labels into what later classifiers learn from). A note whose body is empty apart from frontmatter gets no vector. Long notes are split into chunks of at most 512 tokens (special tokens included); the note vector is the L2-normalised mean of the L2-normalised chunk vectors. Only the first 64 chunks (~32k tokens) of a note are embedded, so one huge note can't hold the job for minutes.
- **Storage:** `note_embeddings`, little-endian `f32` BLOBs, keyed by note and model so two models can coexist during a switch; `content_hash` is the SHA-256 of the embedded text, so a save that doesn't change it (or changes only frontmatter) doesn't re-embed. Vectors are as sensitive as the text, so they live only in the vault: no cache file, no temp files (SQLite `temp_store = MEMORY`, the model is loaded from memory). Trash drops a note's row; restore makes it dirty again.
- **Background job:** starts after unlock. It reads a note's text, embeds it and writes the vector in batches of 32, taking the vault lock only to read a batch and to write its results, never while the model runs. It uses a vault accessor that does **not** count as activity, so indexing never postpones auto-lock. It stops on lock (checked between model runs) and never touches a vault unlocked later. It works from an **embedding queue** (2026-10-25, #46) instead of rescanning the vault: `embedding_dirty(note_id → notes ON DELETE CASCADE, version)`, filled by SQLite triggers on `notes` (insert; update of title, body or `deleted_at`), so every write that can change the embedded text queues the note in its own transaction, whatever code path made it: create, save, rename, import, bulk edits, accepting suggestions, create-tag-from-group, trash, restore. A folder move doesn't change the embedded text and isn't queued. When idle the job checks once a second whether anything is queued (or a model switch or tag description is pending); its own writes never wake it. A pass reads the queue in pages of 500, keeps the per-note content-hash check (a frontmatter-only save is dequeued without re-embedding; an empty or trashed note loses its vector), and writes each batch's vectors and removes their queue rows in one transaction. A pass hands the related-notes index only the notes it embedded, emptied, saw trashed or deleted (a trigger records hard deletes in `embedding_gone`, ids only), instead of diffing every stored hash; the full diff runs only when the index is first built for the ready model. A queue row is only removed at the `version` it was read at, so a save made while the model ran is embedded next. Switching models queues every live note. Migration 8 queues every live note once, so an upgraded vault is checked once. **Safety net:** once per unlock, after the queue is first empty, the job runs the old full hash scan a page at a time (queued notes go first between pages) and queues whatever a code path missed, printing only the count to stderr. It pauses 5 ms between pages: the vault mutex isn't fair, and without the gap a related-notes lookup waited up to 3 s for the ~33 s the scan takes at 1M notes. **Measured** with the scale benchmark (#45) at 1M notes on the 4-core Linux container: save-to-vector 0.01–0.7 s (was 34 s; the rest is the 1 s poll), 1 pass per save (was 2 full rescans), and a pass with nothing to do is no longer run at all (was 34.6 s); unlock-to-related 34 s (was 59 s), still bounded by building the related-notes index (#47). While 10 or more notes are pending the left pane footer shows `Indexing: 1,234 of 20,000 notes indexed` (see First chunk first); fewer (a single save) are embedded without it. A loaded model holds no note data and is kept across lock/unlock.
- **First-time indexing of a large vault** (2026-10-25, #49):
  - **No cross-note batching** (tried and removed): the job hands the model 32 notes per call, but each note still runs on its own (its chunks 8 at a time). Running chunks of several notes in one ONNX call was measured on the Windows dev machine (16 cores, 8 used, 1,000 synthetic notes): 2.6 notes/s batched vs 2.5 one at a time, while the vectors moved (cosine down to 0.990, up to 0.043 per element). The bundled int8 export quantises activations dynamically with one scale per tensor, over the whole call including padding, so a note's vector would depend on the notes it happened to run with. Not worth 4%.
  - **Most recently updated first:** the queue is read newest `updated_at` first (keyset on `(updated_at, id)`), so the notes in use get vectors first. A queue of up to 5,000 notes is sorted; a longer one is read by walking the `notes_updated` index and keeping the queued notes, so a page never sorts the whole queue.
  - **Progress:** the footer shows `Indexing: 1,234 of 1,000,000 notes indexed, ~5 h left`, the time left from the rate over the last minute (once there are 10 s of it). With 10,000 or more notes left it adds "Indexing pauses when the vault locks."
  - **Auto-lock is unchanged:** indexing never postpones it, and there is no "keep unlocked while indexing" switch (Captain's call on #49, 2026-10-25). Indexing resumes after the next unlock where the queue left off, recent notes first.
  - **First chunk first** (2026-11-01, #106): on the CPU the model embeds about 6.5 chunks a second whatever the note (#105), so a backlog of long notes (13–32 chunks) used to index at 0.2–0.5 notes/s. Indexing now has two phases. **First phase:** every queued note gets a vector from its first chunk only (≤ 512 tokens), about one chunk's time per note; a one-chunk note gets its full vector and leaves the queue. **Second phase**, once no note waits for a first chunk: long notes get their full vector (mean of all chunk vectors, as before), one note at a time (a GPU model: a group of notes per call, see GPU indexing, #111). A save queues the note for its first chunk again; the second phase checks between calls (only when the vault's change counter moved, so the check costs nothing otherwise) and stops, so that note goes first.
    - **No schema change.** A first-chunk vector is stored in `note_embeddings` with `content_hash` = SHA-256(`"hush first chunk\0"` ‖ the text's hash), which never equals the full hash, and its queue row stays with `version` = -1. Queue triggers add 1 on every queueing, so a save moves the note back to the first phase (-1 → 0) by itself. A queued note whose stored hash is the first-chunk hash of its current text (a frontmatter-only save, the safety net) goes back to the second phase without being embedded again. An older Hush opening the vault sees ordinary queued notes and embeds them whole.
    - **The model becomes ready after the first phase:** every note then has a usable vector, so Related, suggestions and Discover work while long notes are completed. On a model switch this means the old model's full vectors are dropped once every note has a first-chunk vector from the new one, rather than once the new vectors are complete.
    - **Tag training waits for full vectors:** notes in the second phase stay queued, and the training job already waits while anything is queued, so heads train once on full vectors instead of again as each partial vector is replaced. Its "queue stalled" check now watches both phase counts, since the first phase moves notes between them without shrinking the queue.
    - **Progress:** the footer and Settings → Model show `1,200 of 5,000 notes indexed, 300 of 1,200 complete`; the time left is for the phase running. The measured notes/s per model (Settings → Model's switch estimate) comes from first-phase passes, since that is what a switch waits for.
    - Cost at 1M notes: no extra scan per save. The second phase reads the queue twice as often as before (a page per 500 notes), and per call (a note, or a GPU group) does one `change_count()` call; when something changed it runs `SELECT … WHERE version >= 0 LIMIT 1` over `embedding_dirty` (integer rows, a few tens of ms at 1M [estimate]).
  - **Why the Windows benchmark measures 2.5 notes/s:** its synthetic notes average 302 words but **935 tokens** (2.22 chunks of up to 512), because WordPiece splits the made-up words into several tokens each; that is about 5.6 chunks of ~420 tokens a second on 8 cores. Real English runs about 1.3 tokens a word, so a 300-word note is one chunk of ~400 tokens and should index 2–3 times faster [estimate, not measured]. Re-measure on a real vault before trusting the 4.6-day figure for 1M notes.
- **Measured speed** (release build, 2 of 4 cores of a shared Linux cloud container that was also compiling, so a pessimistic figure; measured with the **fp32** export of the same model, `Xenova/bge-small-en-v1.5` `onnx/model.onnx`, because the int8 file couldn't be fetched there; int8 is usually faster on CPU): fixture vault 24 notes in 0.6 s (**~40 notes/s**, short notes); synthetic 10k-note vault of ~150 words per note in 768 s (**~13 notes/s**, ~13 min). Model load 1.8 s. An idle rescan of 10k notes (after any change) takes ~350 ms in pages of 500, so the vault is never held for more than a few tens of ms. To be re-measured with the int8 model on the dev machine.

**Tag suggestions** (2026-10-24): the user describes a tag in a sentence ("dreams, nightmares, sleep") and Hush suggests that tag on notes whose meaning is close to the description. Zero-shot: it works without any labelled notes. Accepting and rejecting are remembered as training data for the tag classifiers (below).
- **Descriptions:** `tag_descriptions` (tag, description, vector, model); `tag` is case-sensitive like tags. A tag can be described before any note uses it. Settings → **Tags** lists every tag that is used or described, with its live-note count and an editable description; an empty description deletes the row, and the tag is no longer suggested. Tag names follow the metadata panel's rules (leading `#` dropped, no spaces or commas, and `markdown::is_tag`).
- **Tag lists at 10,000 tags** (#122): the description list and the Classifiers table in Settings → Tags are sorted by note count, highest first (then by name ignoring case). Tags on fewer than 2 notes go into a **Rare tags (N)** group that is closed by default and renders nothing until opened; a tag with a description stays in the main list whatever its count, since it can already be suggested. Each list renders 100 rows at a time with *Show more* (paging rather than a windowed list: no dependency, and rows have inputs of varying height). Grouping is `src/lib/tagGroups.ts`.
- **Embedding a description:** done by the background job with the **ready** model, after the notes, so a description and the note vectors it is compared with always come from the same model. Editing a description clears its vector (saving the same text keeps it); a model switch re-embeds descriptions once the new model becomes ready, and until then the old model's descriptions, vectors and threshold keep serving. Descriptions are embedded with the model's `query_prefix`: for bge that is its retrieval instruction `Represent this sentence for searching relevant passages: `, which gave the best precision on the fixture (0.89 at F1 0.76, against the bare description's 0.80 / 0.73 and `tag: description`'s 0.67 / 0.67). `tag: description` with the instruction reached a slightly higher F1 (0.78) but lower precision (0.82) and ranked an unrelated README first for `journal`; fewer wrong suggestions was preferred (see below).
- **Suggestions** for the open note: score = cosine(note vector, description vector). A tag is suggested when the score is at or above the threshold, the note doesn't have the tag (frontmatter or inline) and the user hasn't rejected it on that note; at most 3, best first. Shown in the metadata panel under the tags: `Suggested: #dream  Accept  Reject`. Reloaded when a note opens and after each save; a save's new vector arrives a second or so later, with the job.
- **Threshold per model**, since scores spread differently per model: the default is the model descriptor's `suggestion_threshold`; the vault setting `suggest_threshold:<model ID>` overrides it (Settings → Tags → Suggestion threshold, for the ready model, with "Use default"). A model Hush doesn't know, without a setting, suggests nothing.
- **bge default: 0.67, measured on the fixture vault — but with the fp32 export of bge-small-en-v1.5, not the bundled int8 file**, because Hugging Face was unreachable from the machine it was measured on. Method: the fixture vault imported with the default rules; five hand-labelled descriptions (dream, journal, ferry, letter, work; 12 positive note/tag pairs, every other pair negative); the threshold with the best F1 over all pairs, the higher one on a tie. Result: positives scored 0.56–0.76, negatives 0.39–0.68; at 0.67 F1 0.76, **precision 0.89**, recall 0.67. The issue's first placeholder, 0.75, would have suggested only one of the 12. Int8 quantisation usually moves cosine scores by about 0.01, but **re-measure with the bundled model before trusting it**: `npm run fetch-model`, then `cargo test --manifest-path src-tauri/Cargo.toml --test tag_suggestions -- --ignored --nocapture` prints every variant's scores, the best threshold and how the current default does; change `suggestion_threshold` in `src-tauri/src/embed/mod.rs` to match. The fixture is small (24 notes), so treat this as a starting point and adjust per vault in Settings.
- **Accept** adds the tag to the frontmatter `tags` (the same `set_frontmatter_field` edit as the metadata panel and bulk edits, so CRLF is kept and a singular `tag` key is folded in), re-derives the note and records an accepted example, in one transaction. The frontend saves pending edits first and reloads the editor after, like a bulk edit, so the next autosave can't write the old frontmatter back; if the pending edit couldn't be saved, accepting does nothing. **Reject** records a rejected example; the suggestion is gone for good on that note.
- **Feedback:** `tag_feedback` (note_id → notes ON DELETE CASCADE, tag, accepted, created_at), primary key `(note_id, tag)`; the latest decision wins. It is user input, not derived: kept while the note is in the trash, hidden from queries, deleted with the note. **Removing a tag by hand** (a save, or a bulk remove) counts as a rejection when the tag can be suggested (it has a description, or the note already has feedback for it); other removed tags are left alone, because typing `tags: [dream]` autosaves `d`, `dr`, … on the way and those aren't decisions. Adding a tag by hand writes no row and clears a rejection of that tag on that note: the tag itself is the positive example.

**Related notes** (2026-10-24): a collapsible *Related* section in the right pane, under Details, lists up to 10 notes closest in meaning to the open note (title and folder, most similar first; scores and reasons since #79, below); a click opens the note. `Not indexed yet` while the open note has no vector.
- **Why related** (2026-10-26, #79): each related note shows its score (the exact cosine of the two stored `f32` vectors, which the rerank already computes; the `i8` index only ranks) as a number and a small bar, and chips for the other reasons that apply: *Linked →/←/↔* (the open note links to it, it links to the open note, both), *2-hop ×n* (notes both link to, notes that link to both, and notes on a two-step path either way), up to two shared `#tags` and `+n`, *Folder*, *Author*, *Topic* (same value, case-insensitive). The hover text and an expand button give the full breakdown with the names. `related_notes` returns `{ note, score, reasons }`. **Cost:** reasons are computed only for the ≤10 notes shown, after the rerank, with three queries in total (links from all of them, links to all of them by title, their tags) and one resolution per distinct target, never per pair; only links that resolve to exactly one note count. Two-step lists are capped at 5 names each. **Shared terms** (words frequent in both notes and rare in the vault) were left out: FTS5's `fts5vocab` can count a term per document only by scanning the term's whole posting list, so per-note top terms need stored per-note term vectors, which the issue said to skip. **Measured** (`tests/related.rs` 10k bench, now with two links and a tag per note so the reasons have work; release build, 4-core Linux container, 3 runs each): `related_notes` median 2.8–3.6 ms on main → 3.6–3.9 ms with reasons, worst 4.7 → 5.6 ms. The 1M scale benchmark was not rerun: its synthetic notes have no links, and the added queries are index lookups for 11 notes whose cost does not grow with the vault, except the links *to* them, which grows with how often their titles are linked.
- **Ranking:** cosine similarity. A brute-force scan of the `i8` copy of every vector of the ready model picks the best **100** candidates; those are reranked by the exact cosine of their stored `f32` vectors (read from the vault), so the order is the exact one in practice (#47: on a seeded 10k set the top 10 equal exact cosine's, ties aside). No ANN library (HNSW etc.): the exact `i8` scan is fast enough at 1M, adds no dependency, and adds no second structure holding sensitive data; revisit above ~3M notes. The note itself and trashed or deleted notes are left out; notes without a vector are never candidates.
- **In-memory index** (`src-tauri/src/embed/related.rs`): the ready model's unit vectors quantised to `i8` with one `f32` scale per note (`max|x| / 127`, so each note uses the full `i8` range; the issue's fixed scale 127 wastes most of it, since a 384-dim unit vector's components are mostly under 0.2), in one contiguous `Vec<i8>`: 384 bytes a note, about 0.4 GB at 1M instead of 1.5 GB (`Zeroizing`, grown by copying so no unzeroed buffer is freed). Stored vectors in the vault stay `f32`; no schema change. The scan is a 16-lane integer dot product over half the cores (one thread per 20,000 notes at most), each thread keeping its best in a bounded heap. The index is held by the `Session` beside the vault under its own lock, so the scan never waits for the vault; only the rerank (101 vector reads) and the summaries take the vault lock. Dropped (zeroed) on lock and on unlocking another vault; a job of an old unlock can't write it back.
- **Kept in sync by the embedding job:** after every pass it loads the vectors of the notes that pass embedded and drops the notes that lost theirs (emptied, trashed, deleted) (#46). It rebuilds when the index is first built after unlock or `embedding_model_ready` changes: the stored vectors are read front to back in pages of 500 and quantised into a new index as they arrive (no copy of every `f32` vector; the old index serves until the new one replaces it). The Suggestions view scores every note from the `i8` vectors and gives the notes it shows their exact score from the stored vectors. The lookup still checks that each result is live, so a note trashed a moment ago never shows. When the index changes the backend emits `related-changed` and the panel refreshes; it also refreshes when another note opens, never per keystroke.
- **Speed** (release build, shared 4-core Linux cloud container, not the dev machine; `tests/related.rs`, ignored test): 10k notes × 384 dims, `related_notes` median **4.9 ms**, worst 5.7 ms over 50 lookups; loading the whole index after unlock 0.29 s, in pages of 500.
- **Measured at 1M notes** (#47, scale benchmark, 4-core Linux container; before → after): `related_notes` median 545 → **83 ms**, worst 2.7–8.7 s → **101 ms** (of the 83 ms: scan ~69 ms, reading the 101 vectors ~8 ms, rerank 0.1 ms); peak RSS during unlock + index load +3.1 GB → **+457 MB**; unlock to the first related notes 34 → **11.6 s**. The worst case was lookups starved of the vault lock by the safety-net scan, see Background job.

**Tag discovery** (2026-10-25): Settings → Tags → *Discover tags* groups notes by meaning so the user can see which tags the archive needs, and turns a group into a tag.
- **Scope:** *All notes*, *Notes without tags* (frontmatter or inline), *A folder and its subfolders*, or *Search results*: every note matching the sidebar's current search (text and filters, unranked, no 200 cap). Only live notes with a vector from the ready model are grouped. The ids in scope are read in pages of 10,000; all scopes but search walk the `notes_folder_title` index, which has the id of every live note, so no note body is read.
- **Sampling** (#50): a scope of more than **20,000** notes is grouped from a random sample of 20,000 (partial Fisher-Yates from the fixed seed over the sorted ids, so the same notes give the same sample). Every other note in scope then joins its nearest centre in one pass over the stored vectors, read in storage order in pages of 2,000 (front to back is much cheaper than looking each note up), assigned on half the cores; only ids, group numbers and each group's 50 nearest are kept. So memory doesn't grow with the vault beyond the ids (8 bytes a note).
  - **Measured** with the scale benchmark at 1M notes, 50 groups, on the 4-core Linux container: **18.5 s** end to end (was 7.2 min in the same run setup, 6.0 min in the baseline), and the peak RSS during discovery stayed below what the process already held after unlock (was 1.6 GB above it).
- **Grouping:** spherical k-means (cosine on normalised vectors) over the sample's vectors. Hand-rolled (`src-tauri/src/discover/`), no dependency. Seeded with greedy k-means++ (2 + ln k candidate draws per seed, the best kept, as scikit-learn does) from a fixed seed, so the same notes give the same groups; plain k-means++ split well-separated test clusters wrongly for some seeds. At most 100 rounds; an empty group takes the point farthest from its centre. The assignment step uses half the cores. Default number of groups `clamp(round(sqrt(n / 2)), 5, 50)` with n the sample size, capped at n; the user can pick 1–200.
- **Per group:** size, the **50** notes nearest the centre, nearest first (the first 8 are its sample in the list), and 8 distinctive words, from the sampled notes only, by c-TF-IDF (BERTopic's `tf · ln(1 + A / f)`) over title + body without frontmatter, i.e. the embedded text. Each note is normalised to the same weight first, so one long note can't fill a group's words. Words: lowercase letters/digits, 3–30 characters, not only digits, English stop words and bits of URLs removed.
- **Create tag from group:** a form with the tag name (pre-filled with the top word), a description (pre-filled `Notes about <top 5 words>`) and the group's 50 nearest notes as checkboxes (all checked, nearest first); a group with more members also offers **Select all N notes in this group**, on by default. The backend keeps the latest run's member ids (in memory, until the next run, closing the dialog or lock) so *Select all* names the group rather than sending its ids; members trashed since the run are left out. One command does it all in one transaction: the bulk *Add tag* edit (same code as `edit_notes_metadata`), the description in `tag_descriptions` (an empty one leaves an existing description alone) and an accepted `tag_feedback` row for every chosen note that now has the tag. Notes whose frontmatter can't be read are skipped and get no feedback.
- **Nothing is stored:** results are recomputed on demand and live only in the open dialog (and the members' ids in the backend, see above); closing it cancels a run and drops them, and lock reloads the page. No temp files.
- **Job rules as for embeddings:** runs off the main thread, reads the vault through the quiet accessor in pages of 500 (never holding it while computing), doesn't count as activity (starting a run does), and stops on lock, on a newer run or on cancel.
- **Measured** (Linux cloud container, 4 cores of which the assignment step uses 2, release build; synthetic 384-dimension vectors, so speed only): 10,000 notes into 50 groups in **1.2 s** with clustered vectors and **2.2 s** with structureless vectors (32 rounds), end to end. A debug build (`tauri dev`) takes about 25 s. Fixture vault with the **fp32** export of bge-small-en-v1.5 (the int8 file couldn't be fetched there), 24 notes into the default 5 groups: both dream notes share a group, 2 of the 3 journal notes share another (the third, *Rain*, joins the dreams). Re-run on the dev machine: `cargo test --release --manifest-path src-tauri/Cargo.toml --test discover_tags -- --ignored --nocapture` (after `npm run fetch-model`).

**Tag classifiers** (2026-10-25): every tag gets a small classifier ("head") trained on the user's own notes, on their machine, once it has enough examples; suggestions then come from it, and get better as the user accepts and rejects them. The embedding model never changes; only the head is learned.
- **Model:** one-vs-rest logistic regression per tag on the fixed note vectors, hand-rolled (`src-tauri/src/classify/`, no ML crate): weighted mean log loss + L2 on the weights (not the bias), L-BFGS (memory 10, Armijo backtracking) in `f64` on mean-centred vectors (the bias is converted back), warm-started from the tag's previous head, deterministic.
- **Examples:** positives are live notes with a ready-model vector that have the tag (frontmatter or inline) or on which it was accepted; negatives are every other such note, weight **3** if the user rejected the tag on it (or removed it by hand, which #24 records as a rejection), else weight **1** (an untagged note doesn't really mean "not this tag"). The two classes are then **balanced** (scaled so each has half the total weight, keeping the 3:1 ratio within negatives); otherwise a tag on 2% of the notes would never reach probability 0.5.
- **When a tag gets a head:** at least **10** positives and 10 negatives. Below that it falls back to #24: the description vector, blended with the unit-length centroid of its positives when it has some (`normalize(d + (n/10)·c)`, so 1 example adds a tenth, 9 almost as much as the description), compared by cosine against the model's suggestion threshold. A tag without a description and without a head isn't suggested. A tag **with** a head is suggested with or without a description.
- **Suggesting:** at probability **≥ 0.5**. #24's rules still apply: at most 3, not a tag the note has, not one rejected on it. Classifier suggestions come before description ones (their scores aren't comparable, and a head has learned from the user's own notes); within each, best score first. The metadata panel's tooltip says which it was.
- **L2 = 0.03**, picked on the measurements below: with weaker penalties a head memorises the untagged notes that belong to the tag — exactly the notes worth suggesting it on. At 0.001 a 10-example head suggested 10–13 of 25 such notes; at 0.03, 18–24, with no loss of precision.
- **Storage:** `tag_heads` (tag PK, model, weights BLOB of little-endian f32s, bias, n_pos, n_neg, precision, recall, trained_at, inputs). Derived data, so migration 7 only adds the table. `inputs` is a SHA-256 of everything the head was trained on (training version, model, every vector's note id and content hash, the tag's positive and rejected note ids): a head is retrained only when it changed. Heads for another model are ignored at once (the tag falls back to its description) and deleted and retrained by the next pass; so are heads of tags that drop below 10 examples. A head for a model that stopped being ready while it trained is refused.
- **Training job** (`classify/job.rs`): a background thread started on unlock next to the indexing job. It runs a pass right after unlock (heads that went stale while locked), then whenever the vault changed (SQLite's change counter, checked once a second) and has been quiet for **30 s**, so an import or a burst of edits trains once. Same rules as the embedding job: only the quiet vault accessor (doesn't count as activity, never postpones auto-lock), the vault is held only to read a page of 500 vectors or write one head, never while computing; it stops on lock (checked between tags and between folds). Vectors read for training are zeroised when dropped. A failed pass is logged (no note content) and retried after the next change. After a pass that changed a head it emits `tags-trained`.
- **Quality:** stratified **5-fold cross-validated** precision and recall at 0.5 (folds shuffled with a seed from the tag name, so retraining the same data gives the same numbers), stored with the head. Settings → Tags → *Classifiers* shows per tag: examples (`with / without`, rejections in the tooltip), status (`Trained`, `Training soon`, `Description only · needs N more examples`, `Needs N more examples`) and precision/recall. Precision counts untagged notes the head would suggest as mistakes, so in a vault where a tag is used on only some of the notes it fits, precision reads low even when the suggestions are right.
- **Measured** (release build, shared 4-core Linux cloud container, not the dev machine; vectors from the **fp32** export of bge-small-en-v1.5 because the int8 file couldn't be fetched there; `cargo test --release --manifest-path src-tauri/Cargo.toml --test tag_classifier -- --ignored --nocapture`, after `npm run fetch-model`, re-measures):
  - **Fixture vault:** the import rules tag only **3** notes `journal` and **1** `dream`, so 5/10/20/50 positives can't be measured there; neither tag reaches 10 examples, and a 3-fold cross-validation of `journal` finds none of them (recall 0; its few guesses are wrong, precision 0).
  - **Synthetic notes instead:** 360 notes built from dream-like, journal-like and other sentences (2–4 per note, one from another class in a third of them), embedded with the model. Train on k positives, 3k negatives and k/2 (min 2) notes of the tag left untagged; test on the rest; 5 draws per k. Template sentences are far easier than real notes, so treat these as an upper bound and the shape of the curve as the finding:

    | positives | journal precision / recall | untagged found | dream precision / recall | untagged found |
    |---|---|---|---|---|
    | 5 | 0.99 / 0.71 | 9/10 | 1.00 / 0.95 | 9/10 |
    | 10 | 1.00 / 0.84 | 18/25 | 1.00 / 0.96 | 24/25 |
    | 20 | 1.00 / 0.91 | 41/50 | 1.00 / 0.98 | 49/50 |
    | 50 | 1.00 / 0.94 | 121/125 | 1.00 / 0.98 | 123/125 |

    Precision stays near 1 from 5 examples; recall keeps improving to 20–50. 10 examples, the issue's guess, is a reasonable start.
  - **Training time on 10k notes** (an encrypted vault with 10,000 notes and 384-dimension vectors): **0.23–0.33 s per tag** for training plus 5-fold cross-validation (tags on 2%, 5% and 33% of the notes); the first pass for 4 tags took 2.7 s, of which ~1.75 s is reading and hashing the 10k vectors (also the cost of a pass that finds nothing to retrain). So all tags ≈ 1.8 s + 0.3 s × tags: ~17 s for 50 tags. After one rejection only that tag retrains (warm start), 1.8 s in all.

**Suggestions view** (2026-10-25): review one tag's suggestions across the whole vault, to tag many notes at once or to teach its classifier fastest by answering the notes it is least sure about (active learning).
- **Entry:** *Suggestions* in the left pane toggle (`Tree | Recent | Suggestions`, stored in `sidebar_view` like the others), and *Review suggestions* per tag in Settings → Tags, which opens it for that tag. Pick a tag in the view; the picker lists every used or described tag with how it is scored. The tag is kept until lock. A search or filter shows the flat result list here too.
- **Orders:** *Needs review* (the default when the tag has a classifier) puts the score closest to the scorer's point of doubt first: probability 0.5 for a classifier, the suggestion threshold for a description. *Most likely* (the default otherwise) is highest score first. Ties go to the higher score, then the lower note id.
- **Listed:** live notes with a ready-model vector, scored by the tag's scorer (`Vault::tag_scorers`: head, else description blended with examples), at or above **0.2** probability for a classifier or the suggestion threshold for a description. Left out: notes that have the tag (frontmatter or inline; case-sensitive), notes with any recorded decision for it (rejected, or accepted), trashed notes. The first 100 are shown with the total ("Show more" adds 100). Each row: title, folder, score, a 160-character excerpt of the body without frontmatter, accept and reject. Clicking the title opens the note in the centre pane; the view stays.
- **Scoring** loads the tag's scorer once and applies it to the in-memory vectors of the related-notes index (one dot product or cosine per note; the index lock is released before the vault is taken again for exclusions and titles). Until the embedding job has built the index for the ready model, the vectors are read from the vault in pages of 500 instead.
- **Accept** (a row, or the selection: multi-select as in the note list) is the bulk *Add tag* edit plus an accepted `tag_feedback` row for every note that now has the tag, in one transaction, all or nothing; notes whose frontmatter can't be read are skipped and get no feedback. Open-note handling as for bulk edits: flush, edit, reload (nothing happens if the open note's pending edit couldn't be saved). **Reject** records rejected feedback only; the notes don't change.
- **Retraining:** after every 10 decisions (each note counts; a bulk accept of 15 is 15) the view asks for a training pass at once (`retrain_tags`) rather than waiting for the job: the job trains only after 30 s without changes, and someone answering suggestions changes the vault every few seconds. Passes run one at a time (a pass on demand and the job's own never train side by side). Then the list reloads and re-sorts, keeping the row under the mouse (else the focused row) at the same place on screen. `tags-trained` from the job also reloads it.

## Scale
**Target** (2026-10-25): a vault of **50,000 folders and 1,000,000 notes** must stay fast to read, write and search, with the AI still local. Every earlier timing in this file was measured at 10k notes.

**Benchmark** (`src-tauri/tests/scale.rs`, ignored test): `cargo test --release --manifest-path src-tauri/Cargo.toml --test scale -- --ignored --nocapture`. `HUSH_SCALE_NOTES` sets the size (default 1,000,000; 100,000 for a quicker run); `HUSH_SCALE_VAULT=<path>` keeps the generated vault and reuses it next time (it is checked against the generator version and size).
- **Synthetic vault**, deterministic (fixed seeds, no dependency): an encrypted temp vault, notes over `notes / 20` folders (50,000 at 1M) up to 5 levels deep; bodies of 100–1,500 words, skewed short (mean ≈ 300), Zipf-distributed words with the 250 most common English words on top (so `t`/`th`/`the` hit frequent terms as in real text) and a quarter of each note from one of 500 topics; frontmatter with 0–3 tags; imported through `import_notes` in batches of 500. Nothing is written outside the temp dir and nothing is committed.
- **Fake embedder** (384 dimensions, words hashed into buckets), so the numbers are the job's bookkeeping; the real model's throughput is measured on the first 1,000 notes when `npm run fetch-model` has been run (skipped otherwise).
- **Measured:** (1) save-to-vector latency with the job running as in the app (1 s poll); (2) full passes per save and the time of a pass with nothing to do; (3) unlock (open + KDF) to the first `related_notes` answer; (4) `related_notes` median and worst over 50 random notes; (5) peak RSS during unlock and index load (Linux: `VmHWM` after resetting it); (6) real-model notes/s; (7) search for `t`, `th`, `the` and a two-word query (median of 5); (8) *Discover tags* end to end with the default group count, and its peak RSS.

## Activity panel
- **What** (2026-10-26, #78): a panel at the bottom of the workspace (the *Activity* button in the left pane's footer, the footer's indexing line, or Ctrl+J) with one row per background job: embedding, related-notes index, tag training, safety-net scan, import, Discover tags, migrations, tag rules (#122). Each row shows its state (idle / waiting / running / paused / stopped / failed), what it is doing now, progress, rate over the last minute, time left, how long the current run has taken, the last run (when, how long, what it did) and why it waits or is paused (import running, 30 s quiet period, queued notes go first, no model ready). Below the jobs: live notes, notes with and without a vector, the embedding queue, the model (loaded / ready), cores in use, the related index's size and memory, schema version, and every trained tag head with when it was trained. Next to it an **event log**: passes started and finished with counts and durations, model loaded, index rebuilt, head trained, errors; newest first, filterable by job, with a *Copy* button for bug reports.
- **Note internals**: a collapsed *Internals* section in the details panel shows the open note's id, folder, created/updated times, words and characters, the SHA-256 of the text the job embeds, its vectors (per model, and whether they match the current text), whether it is queued, backlink and outgoing link counts, and each tag's source (typed by hand, or an accepted suggestion).
- **How**: jobs report into one `activity::Activity` held by the `Session` instead of emitting their own events. Reporting takes that struct's own mutex for a moment, never the vault's. One thread sends the whole snapshot as `activity-changed`, at most every 250 ms: changes made meanwhile go out together, and the last change always goes out. `activity_status` returns the same snapshot. The `index-status` event and the footer's indexing line stay as they were.
- **Counts on a timer, only while the panel is open**: every 2 s, through `with_vault_quiet` (not activity, never postpones auto-lock), and only through index lookups (`live_note_count` is all notes minus the trashed ones' partial index, so no row is read). The jobs themselves report numbers they already have.
- **Migrations** run while the vault opens, before the workspace exists, so the unlock screen keeps showing their progress; the panel shows the last one (when, how long, how many notes) once unlocked.
- **Privacy rule**: the activity state and the event log live in memory only. They are never written to disk, `config.json`, `localStorage` or stderr, and the *Copy* button only puts on the clipboard what the panel shows when the user asks. Messages hold counts, durations, model and tag names and error kinds, never note text or titles. Everything is cleared, and its strings zeroed, on lock and on unlock; a job still running for an older unlock can't report into a newer one (each report names its unlock). The log keeps the newest 500 entries. Small routine runs (the pass after an autosave) update the job's last run without a log entry, so they don't push everything else out.

## Model section
- **What** (2026-10-26, #82): Settings → Model shows the vault's model (name, ID, size on disk, vector dimensions, chunk size, licence link) and its state: ready, loading, missing file, checksum failed, unknown to this version, or indexing N of M. Below it, every model Hush knows (`MODELS`), each marked as on this computer or not (the file that is missing or fails its checksum is named). Only models on this computer can be picked. *Check again* re-hashes the files and restarts indexing if it had stopped on them (after the user put the files back).
- **Availability** is decided by the files alone: present in the models folder and matching the descriptor's SHA-256. Files are hashed in 64 KB pieces, and a result is kept until the file's size or modification time changes, so opening Settings doesn't hash 34 MB each time. No network code; `cargo tree` still shows no HTTP client.
- **Switching** goes through a confirmation that every note will be embedded again, with an estimate: the vault's live notes divided by the model's rate. The rate is the last one the job measured for that model on this machine (a pass that embedded at least 50 notes; kept per model ID in `config.json` as `index_rates`, which holds model IDs and numbers only), else 2.5 notes/s, the bundled model on the Windows dev machine (Scale), labelled as an estimate. The switch itself is the existing `set_embedding_model` (queues every live note); the old model's vectors keep serving related notes and suggestions until the new ones are complete, and tag classifiers retrain for the new ready model. If the job had stopped (its model couldn't load), the switch starts it again. No schema change.
- **Reduced functionality**: related notes, tag suggestions, tag classifiers and Discover tags need a ready model; search and everything else don't. They count as off while the vault's model can't be loaded (missing, checksum, unknown, load error), and while no model's vectors cover every note yet (loading, first index). A switch alone doesn't count: the old vectors serve. A model that fails to load counts even when old vectors exist, because new and changed notes get none.
  - The **footer** keeps a line with the short reason and a link to Settings → Model for as long as that lasts (no dismissable pop-up). During the first index it shows the usual `Indexing N / M` line plus one saying related notes and suggestions start after it.
  - The **Activity panel** shows a *Model* row above the jobs with the reason, the features that are off and the same link.
  - **At the point of use** the related-notes section, the note's tag suggestions, the Suggestions view, Discover tags and the Classifiers table show one line naming the reason with the link, instead of looking empty.
- **Where the state comes from**: only what the job already knows, so it costs no vault access. At the start of every pass the job reports the vault's `embedding_model` and `embedding_model_ready` it reads anyway (`EmbedderSource::vault_models`), and the app's model loader records how loading went (`embed::models::ModelTracker`). Changes go to the frontend as `model-status`; `model_status` returns the same. On a new unlock the vault part is forgotten until the job's first pass reports it.

## Optional models
- **What** (2026-10-26, #83): besides the bundled default, Settings → Model offers optional models, downloaded in the app or loaded from files. The default stays bundled; nothing is downloaded unless the user clicks *Download* for one model.

| Model | ID | Licence | Size | Why |
|---|---|---|---|---|
| `BAAI/bge-small-en-v1.5`, int8 (`Xenova/bge-small-en-v1.5`) | `bge-small-en-v1.5-q8` | MIT | 34 MB | Bundled default, English |
| `intfloat/multilingual-e5-small`, int8 (`Xenova/multilingual-e5-small`) | `multilingual-e5-small-q8` | MIT | 135 MB (118 MB model + 17 MB tokenizer) | About 100 languages, for vaults not in English. Prefixes `passage: ` / `query: `, mean pooling, 384 dimensions, 512 tokens |
| `sentence-transformers/all-MiniLM-L6-v2`, int8 (`Xenova/all-MiniLM-L6-v2`) | `all-minilm-l6-v2-q8` | Apache-2.0 | 24 MB | Faster English model (6 layers instead of 12) for the first index of a large vault. Mean pooling, 384 dimensions, 256 tokens |
| `BAAI/bge-small-en-v1.5`, fp16 (`Xenova/bge-small-en-v1.5`, `model_fp16.onnx`) | `bge-small-en-v1.5-fp16` | MIT | 68 MB (67 MB model + 0.7 MB tokenizer) | Made for the GPU (#105, see GPU indexing). Same model and vectors' meaning as the default, CLS pooling, 384 dimensions, 512 tokens; threshold 0.67 as the int8 model |

  Each file's URL, SHA-256 and size are pinned in its descriptor (`src-tauri/src/embed/mod.rs`); a test checks every optional file has all three and an HTTPS URL. All load through the same `ModelDescriptor` path as the default. Suggestion thresholds for the optional models (E5 0.8, MiniLM 0.4) are not measured yet; re-measure with `measure_suggestion_threshold_on_the_fixture_vault` once the files are on a dev machine.
- **Where they live:** the `models` folder in the **local** app data folder (`%LOCALAPPDATA%\<app id>\models` on Windows, `~/.local/share/<app id>/models` on Linux), per machine and outside any vault. Not the roaming folder that holds `config.json`: a roaming profile would copy 100+ MB between machines. The bundled default stays in the resource folder. Loading looks in both (the likelier first) and checks the SHA-256 as before, so a damaged install can also be fixed by importing the default model's files.
- **Download** (`embed::download::Downloader`): shows size and host on the button before anything starts. Writes `<name>.part` and continues it with an HTTP `Range` request after a cancel, a crash or a dropped connection. A server that ignores `Range` (answers 200) gets a full restart. The whole file's SHA-256 is checked before `.part` is renamed. On a mismatch the `.part` is deleted and the error shows both checksums, so an unverified file is never loaded. Progress (bytes, %, speed over the last 3 s) and *Cancel* are in Settings. Downloads run on their own thread and need no vault, so they carry on while it is locked; a finished download re-checks the model files and restarts indexing if it had stopped for want of them.
  - HTTPS only, redirects included (Hugging Face redirects file URLs to its CDN; `ureq` refuses a redirect to plain HTTP). The request is a plain GET with `User-Agent: Hush` and, when resuming, `Range`: no note content, vault path or identifier, no telemetry, no version check, no other request.
  - Proxy: `HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` from the environment, else on Windows the system proxy set in Windows settings (registry `ProxyEnable`/`ProxyServer`, `ureq`'s `win-system-proxy`). PAC scripts and per-protocol proxy lists (`http=…;https=…`) are not supported. Certificates are checked against the system's store (`rustls-platform-verifier`), so a company proxy whose root certificate is installed works.
  - Errors say what went wrong in plain terms: host not found (offline or DNS), can't connect, connection dropped (Download again to continue), timed out (20 s to connect, 60 s without data), TLS failure, proxy refused, HTTP status.
- **Manual import** (*Load model file…*): for offline machines, or users who don't want Hush online at all. The picked files are matched to the model's files by SHA-256, whatever their names (`model_quantized.onnx`, `tokenizer.json` as downloaded from the model page). Each is copied into the models folder through a `.part` and checked again. A file that matches neither is refused with the expected and actual checksum.
- **Remove**: deletes a downloaded or imported model's files. Refused for the bundled model, while it downloads, and while the open vault embeds with it or its vectors serve (the message names the vault). Another Hush process with another vault open isn't known about; if that vault uses the model, its loaded copy keeps working until restart, after which it shows the missing-model state.
- **Tested** against a local HTTP server (`tests/model_download.rs`): complete download, resume after a dropped connection (checks the `Range` header and that only the rest was sent), resume after cancel, a server without ranges, checksum mismatch (file deleted, nothing renamed), HTTP error status, nothing listening, import accepted and refused, removal guards. Not tested in CI: the real Hugging Face URLs, the Windows system proxy, and TLS through a company proxy.

## GPU indexing
- **What** (2026-11-03, #105): on Windows a model made for the GPU (`ModelDescriptor.gpu`; today only `bge-small-en-v1.5-fp16`) runs on the GPU through ONNX Runtime's **DirectML** execution provider. Other models and other platforms stay on the CPU. Turning it off: Settings → Indexing → *Use the GPU for models made for it*, kept per machine in `config.json` as `index_gpu_off` (default on).
- **Measured** (`bge-small-en-v1.5`, release builds, branch `issue-105-directml-prototype`):

| Machine | Model, device | 3,000-word notes | 300-word notes |
|---|---|---|---|
| ZOLDER, RTX 4060 Ti 8 GB | fp16, DirectML, 8 chunks per run | **17.9 notes/s** | **129 notes/s** |
| ZOLDER | int8 (bundled), CPU | 0.41–0.50 notes/s | |
| Work laptop, Core Ultra 7 155H, Arc iGPU | fp16, DirectML | 1.90 notes/s | |
| Work laptop | int8, CPU | 1.39 notes/s | |

  So a discrete GPU indexes long notes about 35–40× faster than the CPU, and an integrated GPU about 1.4× (not worth a 68 MB download). The laptop's NPU (Intel AI Boost) isn't reachable through DirectML; it would need OpenVINO, not tried. At 17.9 notes/s a first index of 1M long notes takes about 15.5 h instead of 1.5–2.5 days.
- **Not automatic; offered in Settings → Model** (Captain's call, 2026-11-03). Hush lists the DXGI adapters on startup; when one is **discrete** (≥ 1 GiB dedicated memory) and GPU use is on, Settings → Model says so and offers the fp16 model next to the current one. Switching is the ordinary model switch (download, confirm, re-embed every note); the estimate uses the measured rate once there is one, else 15 notes/s with a discrete GPU. Nothing switches by itself: a switch re-embeds the whole vault, and the vectors would differ slightly between machines that sync one vault.
- **Not bundled.** The fp16 file is an optional download (68 MB, pinned URL and SHA-256 like the other optional models), so the installer only grows by DirectML.dll.
- **DirectML.dll ships next to hush.exe.** The copy in `System32` (1.8.0 on the measured machines) fails on the first run with `E_INVALIDARG`, so the installer carries the one `ort` downloads with ONNX Runtime: `build.rs` copies it from the build's profile folder to `src-tauri/directml/` (gitignored) and `tauri.windows.conf.json` bundles it beside the executable. Windows loads the DLL beside the executable before `System32`. `onnxruntime` imports DirectML.dll statically, so hush.exe needs a loadable DirectML.dll to **start** (a damaged copy stops it with 0xC000012F before any Hush code runs, so there is nothing to fall back from). Delay-loading it was not done: a missing DLL would then crash at the first GPU run instead of at startup, which is not better. Windows 10 and later have D3D12, which is all the shipped DLL needs; on older Windows hush.exe would not start [not tested].
- **In the app** (ZOLDER, 50 synthetic 3,000-word notes, release, `tests/gpu_model.rs`): the indexing job does **10.9 notes/s** on the GPU (11.1 through the same path without the vault; 18.5 with 32 whole notes per run) with the fp16 model, and 0.39–0.48 notes/s with the same model on the CPU (about what int8 does there, so without a GPU the fp16 model brings no speed). GPU and CPU vectors agree to a cosine of at least 0.999999. Two fixes got the job there from 5.5 notes/s:
  - The probe at load runs one **full** batch (8 chunks × 512 tokens). A one-sentence probe made every later DirectML run about twice as slow (~87 ms instead of ~41 ms per 8 × 512 run).
  - Every GPU run is **padded to 8 rows** (padding rows have a zero attention mask and are dropped), so DirectML sees one input shape. The job's second phase embeds one note at a time, which gave runs of every size from 1 to 8.
  - The rest of the gap was the job's second phase: it embedded one note per call and each note's first chunk a second time. Vault reads and writes cost about 3%.
  - **Second phase in groups** (2026-11-04, #111): with a model that has `batch_across_notes`, the second phase hands the model the rest of the queue page and the model takes notes until they hold at least **32 chunks** (four full runs of 8; one note longer than that is a group of its own), tokenizing each note once and none past the group. The chunks of the group run 8 at a time across note boundaries, so only a group's last run is padded, and the vectors are split back per note and averaged as before. The job checks for a save between groups instead of between notes, so a save waits for at most one group (32–95 chunks, about 0.2–0.5 s on ZOLDER [estimate from 41 ms per 8 × 512 run]). Queue rows are still removed only at the version read, so a save made while its group runs is embedded again next. int8 models keep one note per call. Per group the job reads nothing more than before: the page is already in memory, and the change check is one `change_count()` call (plus the `LIMIT 1` query only when something changed). Not measured on a GPU yet; acceptance is ≥ 15 notes/s on ZOLDER with `tests/gpu_model.rs`.
  - **The first-chunk vector from the first phase is not reused** in the second: the tokens are the same, but the first phase ran that chunk with other notes' first chunks (other run shape, other padding length), and fp16 on DirectML gives vectors that agree to a cosine of 0.99999, not bit for bit. Reusing it would save one chunk in 6–7 for 3,000-word notes; worth measuring on ZOLDER before relying on it.
- **Installers** (ZOLDER): MSI 52.2 MB, NSIS 46.5 MB; both carry DirectML.dll (18.5 MB) beside hush.exe and `models\` with the int8 model.
- **Falls back to the CPU.** The session is built with `error_on_failure()`, so a missing or unusable GPU fails the load instead of silently running on the CPU, and right after loading the model embeds a short probe text, because the old DLL above loads fine and fails only on the first run. A failure is remembered for that model until restart, *Check again* or the GPU switch is turned on again; the fp16 model then runs on the CPU (slower than int8 [estimate, not measured]) and Settings → Indexing shows why.
- **Batching across notes:** a GPU model embeds the chunks of several notes in one run (8 chunks), which is where the GPU speed comes from. CPU int8 models keep one note per run, because dynamic quantisation scales each run's activations together, so a vector would depend on which other notes shared its run. fp16 vectors don't.
- Session options for DirectML: memory pattern off and sequential execution, as DirectML requires; the high-performance adapter preference picks the discrete GPU on laptops with two.
- Tests on Windows: `cargo test --release` needs `CARGO_PROFILE_RELEASE_PANIC=unwind` (the release profile aborts on panic), and DirectML.dll in `target\release\deps`.

## Graph view
**Graph** (2026-10-26, #80): an Obsidian-style graph of notes and their connections, as a view of its own (header button *Graph*), with the folder tree on the left and the details panel on the right as in the note view. Clicking a note node makes it the open note (the details panel and the local graph follow it) without leaving the graph; double-click or Ctrl+Enter opens it in the editor. Clicking a tag node switches to the global graph of that tag. Notes clicked in the details panel while the graph is shown also stay in the graph.

- **Scale rules.** Hush targets 1M notes, so the graph never loads the vault: the backend command `graph(scope, options)` returns one subgraph, built with index lookups on `links` and `note_tags` for the notes in it, and taking the vault a page at a time (2,000 notes, or 50,000 scope ids) so saves interleave. It runs off the main thread (`spawn_blocking`).
  - **Local graph** (default): the open note and its link neighbours, both directions, to depth 1–3 (slider), breadth first so the closest notes come first. It stops at the node cap, saying "the cap stopped it (N+ found)".
  - **Global graph**: always a scope: a folder with its subfolders (default: the open note's folder), a tag with its nested tags, the sidebar's current search, or the whole vault (an explicit choice, never the default). Above the node cap (default 5,000, 50–50,000) it keeps the most-linked notes, "Showing 5,000 of 182,340 notes, most-linked first". "Most-linked" is links out plus link rows whose target is the note's title (resolved or not), two index counts per note: cheap and close enough for ranking.
  - Folder and tag scopes read only their index range (folder: `notes_folder_title` for the folder and the `folder/`…`folder0` range; tag: `note_tags` for the matching tag ids). The existing tag-discovery scope reader and search filter scan every note from the start for these, which took 0.25 s for a 20-note folder and 2 s for a tag at 1M.
  - Tag and ghost nodes don't count toward the cap; ghosts are capped separately at the same number.
- **Edges.** Links: resolved wikilinks, drawn with an arrow; ambiguous links are left out (they would need one edge per candidate). Meaning (toggle; on by default in the local graph, off in the global one): each note's 5 closest notes **within the graph** at or above the threshold slider (default 0.75), by the exact cosine of the stored `f32` vectors, compared pairwise on half the cores; in the local graph the centre's own closest notes in the whole vault (the related-notes index) join as nodes too. Drawn in the accent colour, thinner and without arrows. They are **not dashed**: sigma has no dashed edge program, and a custom WebGL program was more than this issue needed. Tags (toggle): one node per tag, joined to its notes. Unresolved targets (toggle): ghost nodes, joined by their link.
- **One-note tags** (#122): with *Tags* on, tag nodes of tags that only one live note in the vault has are left out by default; the *One-note tags* toggle next to the edge toggles shows them. Counted in the vault, not in the view, so a tag on many notes stays in a local graph that shows one of them. Only tags on one note in view are looked up, each with a `LIMIT 2` probe on `note_tags_tag`, so a tag on 500,000 notes costs what one on two does. The toggle is a display control like the others (per device, no note data).
- **Display.** Node size by link count in the graph; colour by folder, first tag or topic (a fixed 12-colour palette by hash, so a value keeps its colour; grey for none). Hover highlights a node's neighbours and hides other edges; edge hover says why it exists ("Link: A → B", "Meaning: 0.823 similarity", "Tag #x"), switched off above 5,000 edges where picking edges costs every frame. Labels show on nodes drawn at least N pixels wide (slider). Controls: depth, scope, cap, edge toggles, threshold, colour-by, label threshold, pause/resume layout, fit, and *Forces* (repulsion, gravity, link strength = ForceAtlas2's `scalingRatio`, `gravity`, `edgeWeightInfluence`; ForceAtlas2 has no link distance as such). Drag a node to move it; the layout pauses while dragging. Keyboard: focus the canvas, arrows move to the neighbour most in that direction, Enter opens, Ctrl+Enter edits, Escape clears; the focused note is announced to screen readers.
- **Library:** sigma.js 3.0.3 (WebGL) + graphology 0.26 + graphology-layout-forceatlas2 0.10.1, bundled: +184 KB minified, **+45 KB gzip** for the app chunk, plus a 5 KB worker. Sigma 4.0 came out in October 2026 and was skipped as too new. ForceAtlas2 runs in a module **Web Worker** loaded from the app (`src/lib/graph/layout.worker.ts`), 5 iterations per round trip, 400 per load (Resume runs 400 more); the package's own worker supervisor builds a `blob:` worker, which the CSP (`script-src 'self'`) blocks. Positions are kept by node key for the session, so changing a toggle doesn't scramble the picture. Graph data and the view's settings live in memory only (settings for the unlocked session; nothing stored, since the scope names folders and tags).
- **Measured** (release, 4-core Linux container; `tests/graph.rs`, ignored tests). Synthetic 1M notes in folders of 20, each linking to a hub (every 1,000th note), its successor and one other, and carrying one of 100 tags: local depth 1 **1.3 ms** (6 nodes), depth 2 **0.29 s** (2,014 nodes), depth 3 **0.69 s** (cap of 5,000 reached; 17 s before the search stopped at the cap), a hub at depth 1 **0.14 s** (1,002 nodes); folder of 20 notes **2.5 ms** (0.24 s with the discover scope reader); tag of 10,000 notes cut to 5,000 **1.0 s** (2.0 s with the search filter); whole vault cut to 5,000 **5.3 s**, almost all of it two link counts for each of the 1M notes (an explicit choice, off the main thread, the vault taken 10,000 notes at a time so saves interleave). Meaning edges for 5,000 notes × 384 dims pairwise: **1.1 s**. Frontend (headless Chromium, software WebGL, mocked backend): a local graph of 200 neighbours is drawn **185 ms** after the data arrives (300 ms target), 5,000 nodes in 0.5 s, and zooming a 5,000-node graph ran at 60 fps; this is not the dev machine, so the ≥30 fps check there is still to do.

## Mermaid diagrams
**Mermaid** (2026-10-26, #89): a ```mermaid fence renders as a diagram in Preview and Split; the editor keeps the source.

- **Library:** `mermaid` 12.2.0, pinned exactly, bundled. Nothing is fetched at runtime. It is loaded with a dynamic `import("mermaid")` the first time a rendered note has a diagram, so a note without one never loads it. The startup JS grew by 6.0 KB raw / 3.3 KB gzip (1,104,307 → 1,110,269 B; 369,130 → 372,394 B gzip). The first diagram loads about 716 KB raw / 185 KB gzip; all diagram types together add 5.1 MB of lazy chunks.
- **CSP unchanged.** No chunk uses `eval`, `new Function` or `blob:`. ELK's worker path only runs with a worker URL, which Hush never sets. The `<iframe>` code is for `securityLevel: "sandbox"`, which Hush never uses. No diagram type had to be left out.
- **How:** `markdown.ts` turns the fence into a `.mermaid-block` placeholder with the escaped source. After each `{@html}` update, `mermaid.ts` puts cached SVG back at once; the rest render one at a time (mermaid's render isn't safe concurrently), only within 600 px of the visible area of the preview's scroll container (IntersectionObserver). The cache is an LRU of 200 entries keyed by theme + the exact source, not a hash, so a collision can't show the wrong diagram. While typing (updates < 1 s apart), changed diagrams wait for 300 ms of quiet and the block keeps its last rendering, faded, instead of flashing back to source.
- **Security (imported notes are untrusted):** `securityLevel: "strict"`; `secure` = mermaid's own list plus every theme, font, label and DOMPurify key, so a `%%{init}%%` directive can't change them. The SVG then goes through a second DOMPurify instance (SVG + HTML profiles, `<style>` and `<foreignObject>` allowed, `foreignObject` as an HTML integration point so HTML labels survive, no scripts/frames/forms). Diagram links go through the preview's click handler (`https:`/`mailto:` only). Label `<img>` tags without handlers survive mermaid's own sanitizer, so an `<img src=x>` label can request a same-origin path, the same as a markdown image does today. A diagram's `<style>` is scoped to its own id by mermaid; `classDef` text could still carry CSS, which the CSP keeps from loading anything remote.
- **Errors:** an inline box (`--danger`/`--danger-soft`) with mermaid's message and the source; `suppressErrorRendering` is on and the temporary nodes mermaid puts on `<body>` are removed after every render. Limits: 50,000 characters (checked before mermaid sees the text, since mermaid otherwise draws a "too large" diagram) and 1,000 edges.
- **Theme:** mermaid's `base` theme with `themeVariables` read from the CSS tokens at render time, plus the app's sans font. A `prefers-color-scheme` change re-renders the diagrams; the old ones stay up until the new ones are ready.
- **Measured** (headless Chromium, Vite dev server, so unbundled and slower than the app): a note with 50 distinct diagrams shows its text in 14–23 ms and its first diagram in 0.63–0.67 s cold (mermaid's load included), 60 ms when mermaid is already loaded; scrolling through it renders the rest with the longest frame at 36–40 ms. Check: `node scripts/check-mermaid.cjs` with `npm run dev` running.

## Extensibility
- **No plugins or third-party code** (2026-10-24). Features that would otherwise be plugins (templates, daily notes, custom CSS, …) are built into Hush and requested as separate issues.
- Why: a plugin runs after unlock and sees every decrypted note, and loading one would need the strict CSP relaxed.
- Revisit a sandboxed plugin API (WASM/WebWorker, no network, per-plugin permissions) only if the list of built-in features keeps growing.

## UI
Three panes: left = search, filters, note list / folder tree (sorted by updated); centre = title + editor; right = metadata panel, backlinks, outgoing links, related notes. Side panes collapsible.
- Left pane has a **Tree | Recent** toggle (2026-10-24), stored in vault `settings` (`sidebar_view`, default Tree); *Suggestions* was added to it on 2026-10-25 (see AI classification, Suggestions view). *Tree*: one explorer tree of folders and the notes directly in them (subfolders first, then notes, both by name), root notes at the top level, notes loaded per folder on first expand in pages of 500 ("Show more"). Opening a note any way expands and scrolls to it. Expanded folders survive view switches but not lock. Keyboard: Up/Down, Left/Right, Enter, Home/End. *Recent*: the folder tree plus the flat list by updated. While a search or filter is active, both views show the flat result list.
- **Recently opened** (2026-10-25, #57): a collapsible section at the top of the left pane, above the Tree / Recent / Suggestions content, listing the notes the user last **opened**, most recent first. It is not the *Recent* view, which lists notes by last **edit** (`updated_at`). It shows in all three views, hides during a search or filter and when the list is empty or turned off, and its collapsed state is a vault setting (`recent_opened_collapsed`). Click opens the note as in the tree; the open note is highlighted.
  - **Confidential by construction:** the list is a JSON array of note **ids** under the vault setting `recent_opened`, inside the encrypted vault, never in `config.json` or `localStorage`, and no titles are stored (a rename or move needs no update). Each vault has its own list and it survives lock/unlock.
  - `open_note` (a user open) and `create_note` move the id to the front, dedupe and cut to the count; opening the note already at the front writes nothing. The frontend's internal re-reads of the open note (after a move, a bulk edit, leaving Settings) pass `record: false`, so they never re-add a note the user just cleared. `recent_opened_notes` skips trashed notes but keeps their ids, so a restored note comes back in its old place, and drops ids of notes deleted for good.
  - Settings → *Recently opened notes*: count 0–1000 (raised from 50 on 2026-10-25; the cap bounds the id list rewritten on every open), default 10, with Save and *Clear list*. 0 turns it off: nothing is recorded and the list is cleared. Lowering the count cuts the list at once.
- **Resizable side panes** (2026-10-25, #55): a drag handle on the inner edge of the left pane and of the details panel (`ResizeHandle.svelte`, used for both). Left 200–480 px (default 280), details 240–520 px (default 300); the editor never gets narrower than 360 px: a drag stops there, and a window too narrow for both stored widths shrinks the side panes for display (in proportion to how far each is above its minimum) without changing what is stored. Double-click or Enter resets to the default; the handle is a focusable `separator` with Left/Right (16 px), Home/End. Widths are stored **per device in `localStorage`** (`hush.layout.leftWidth`, `hush.layout.rightWidth`), not in the vault: they hold no note data, and the layout is then the same before unlock and for every vault on that device. No handle shows on a hidden pane or the details rail.
- **Find in note** (2026-11-04, #125): Ctrl+F opens one find bar above the note's panes, prefilled with selected text (one line). Enter / F3 next, Shift+Enter / Shift+F3 previous, both wrapping; Esc closes it, clears the highlights and gives focus back. Case-insensitive by default, with *Match case*, *Whole word* and *Regular expression* toggles. In split view it drives CodeMirror's search (its own panel stays hidden) and the count is the editor's, over the Markdown source; the preview highlights the same query in its rendered text. In *Preview only* it searches the rendered text, so `**bold**` is found as `bold` and a link URL isn't found; matches don't cross blocks, and diagrams are skipped. Replace (Ctrl+H) is editor only. Preview highlights use the CSS Custom Highlight API, so the `{@html}` DOM isn't changed; without it they fall back to `<mark>` wrappers that are rebuilt after each render. Opening another note closes the bar. Matching logic: `find.ts` (tests in `find.test.ts`).
